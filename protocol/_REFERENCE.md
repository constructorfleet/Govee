## 1. BLE GATT transport

- 20-byte fixed packets, written to a vendor service/characteristic.
- Many families use:
  - service `00010203-0405-0607-0809-0a0b0c0d1910`
  - characteristic `00010203-0405-0607-0809-0a0b0c0d2b11`
  but **always read the family's `ble/BleComm.java` / `AbsBleComm` subclass** and report
  the actual UUIDs. Some families override them.
- Notify/read responses arrive on the same characteristic. `AbsController.m()` strips the
  header: for read (`0xAA`) it copies bytes 2..18 into a 17-byte "valid bytes" buffer; for
  write (`0x33`) it copies bytes 3..18 into 16 bytes. Parsers operate on that.

## 2. BLE packet format

Single-packet (most commands), generated by
`com.govee.base2kt.utils.BleUtils.generate20Bytes(proType, cmdType, payload)`:

| offset | len | meaning |
|---|---|---|
| 0 | 1 | `proType` (protocol/op class) |
| 1 | 1 | `cmdType` (command/opcode) |
| 2..18 | 17 | payload (command-specific; unused bytes 0x00) |
| 19 | 1 | BCC = XOR of bytes 0..18 |

`proType` values seen in `AbsSingleController` / `BleProtocolConstants`:

- `0x33` (51) — write / set
- `0xAA` (170, signed -86) — read / query
- `0xA3` (163, -93) — multi-packet write V1
- `0xA4` (164, -92) — multi-packet write V2 / multi read
- `0xA5` (165, -91) — multi write
- `0x3F` (63) — multi write V1 variant
- `0xEE` (238, -18) — notify / OTA prepare class
- `0xEF`/notify variants — device notifications (check family `BleProtocol`)

`AbsSingleController.getValue()` returns:
- write → `generate20Bytes(0x33, cmdType, q())`
- read  → `generate20Bytes(0xAA, cmdType, q())` (q() may be null/empty)

Some controllers override `p()` for the read variant (e.g. `AbsModeController.p()` = `{1}`).

### Multi-packet writes

`MultipleControllerComm` / `MultipleControllerCommV1`: still 20 bytes per packet.
Layout: `[0]=proType`, `[1]=cmdType or 0`, `[2]=package position/index` (starts at 0),
`[3..18]` = chunk, `[19]=BCC`. Last/only packet may use the real cmdType. Report the exact
sequencing/indices used by each family's `AbsMultipleController*`/`MultipleBleBytes`.

## 4. `CmdBuilder` → `Comm` / `Mode` chain (BLE)

Per-SKU scene builders look like:

```java
class BleColorCmdBuilderV1 extends AbsBleCmdBuilderV1<ColorModel> {
  public IBleCmd d(ColorModel m) { return () -> Comm.makeColorController4BleComm(m.h).getValue(); }
}
```

The payload is really built by the family's `pact/Comm.java` and `ble/ModeController.java`.
To get a real payload you must follow:

`*CmdBuilder*.java` → `Comm.makeXxx4BleComm()` → controller (`BrightnessController`,
`SwitchController`, `HeartController`, `ModeController`, family `XxxController`) →
`getCommandType()` + `getWriteBytes()`/`q()`.

### Mode / scene / dynamic effect payloads

`AbsModeController` has `cmdType = 0x05`; payload `q()` = `mode.getWriteBytes()`.
`AbsMode.parse()` reads `validBytes[0]` as sub-mode type, then dispatches to a
`SubMode*` parser with the remaining bytes. Common layouts (from h6159, replicated with
variations across families):

| sub-mode | id | write payload (`q()`) | notes |
|---|---|---|---|
| color | 0x02 | `02 R G B colorTemFlag R2 G2 B2` | 8 bytes; flag=1 means color-temp mode, `R2G2B2` is the temperature RGB; bg color support |
| music | 0x03 | `03 autoFlag sensitivity [R G B]` | 3 or 6 bytes; sensitivity 0..99; autoFlag 0 = manual/color |
| scenes | 0x04 | `04 effectLo effectHi` | 16-bit LE effect code |
| new DIY | 0x0A | `0A diyLo diyHi` | 16-bit LE DIY code |
| music V1 | 0x0E | family-specific (`ParamsSubMode4Music`) | multi-param music/dynamic |
| gradient / multi / carousel / motion | varies | multi-packet, see family `SubMode*` + `AbsMultipleController*` | report layer/segment counts, direction, speed, colors |

Effect definitions are usually in `sku/EffectOp4*.java`, `sku/Support.java`,
`pact/ScenesV0.java`, `ble/SubMode*.java`, `newdetail/diy/*`, `newdetail/music/*`,
`base2light/effectPlay/effect/mode/*` and `base2light/ble/music/*` in the base app.
Report **effect IDs, names, parameter ranges, direction/speed/motion attributes and the
exact byte/JSON layout**, not just class names.

## 5. IoT / cloud protocol

IoT commands are JSON strings produced by `makeCmdStr(AbsCmd)`:

```java
CmdBuilder.makeCmdStr(cmd)  // -> Write.getWriteMsg4Transaction(null, cmd)
```

Write envelope (`com.govee.base2home.iot.Write` + `AbsCmdWrite`):

```json
{
  "msg": {
    "transaction": "<generated>",
    "accountTopic": "<iot account topic>",
    "type": 1,
    "origin": 32,
    "cmdVersion": <int>,
    "cmd": "<command name>",
    "data": { /* AbsCmd subclass fields, serialized by field name */ }
  }
}
```

Read/query envelope (`Read` + `AbsCmdRead`), `type` = 0:

```json
{
  "msg": {
    "transaction": "<generated>",
    "accountTopic": "<topic>",
    "type": 0,
    "origin": 32,
    "cmdVersion": <int>,
    "cmd": "<command name>",
    "data": { /* optional */ }
  }
}
```

Protocol variants `IotMsgProType.V0/V1/V2` change the *incoming* envelope. V1 incoming
fields include `cmd`, `cmdVersion`, `type`, `proType`, `device`, `sku`, `softVersion`,
`transaction`. Report the variant a family parses (look at `WifiNotifyParse`, `IotManager`,
`*NotifyParse`, `pact/Support`).

Common IoT `cmd` names (`com.govee.base2home.iot.Cmd` and per-family `iot/Cmd.java`):

`online`, `turn` (`data.val` 0/1), `brightness` (`data.val`), `status`, `color`
(`data.red/green/blue`), `colorTem` (`data.colorTemInKelvin` + `data.color`), `pt`,
`mode`, `colorwc`, `ptReal`, `multiSync`, `ptUrl`, plus family-specific names
(`timer`, `oscillate`, `mode`, `workMode`, `humidity`, `temperature`, ...).

`pt` = passthrough: raw device command bytes (often base64/hex) sent through the cloud.
`ptReal` = `{ "command": ["<base64(20-byte BLE frame)>", ...] }` — BLE frames tunneled over
IoT, so the BLE table applies verbatim to cloud devices too. `ptUrl` = fetch a command blob
from a URL then execute it. `multiSync` = multi-device sync.

**Important:** if a family has `iot/CmdPtReal`, `CmdPt`, `Op*CommDialog4BleIot*`, or
`DeviceItem4BleIot`, it supports IoT and/or BLE+IoT. Capture which and how BLE frames map to
`ptReal`.

## 6. Determining model/SKU and protocol support

Per split, inspect:

- `<family>/sku/Sku.java` — SKU string constants and arrays (`g`, `h`, ...).
- `<family>/sku/SubLib.java` — `keys()` returns the SKU list for that sub-family.
- `<family>/sku/Register4Item.java`, `Support*.java`, `SubMaker.java`, `SubLib*.java`.
- `<family>/pact/Comm.java`, `pact/Support.java`, `pact/DeviceItem.java`.
- Presence of `ble/` and `iot/` packages and `Ble*CmdBuilder*` vs `Iot*CmdBuilder*`.
- `AbsBleCmdBuilder*.a(...)` / `AbsIotCmdBuilder*.a(...)` support checks.
- `base2light` interfaces implemented: `AbsBleWifiSku`, `AbsBleIotItem`, etc.

Classify each SKU's transports as one or more of: `ble` (GATT only), `iot` (cloud/WiFi
only, incl. `ptReal`), `ble+iot`, `wifi` (LAN/UDP/MQTT), `matter`, `ir/rf`, `thread`.
Record `pactType`/`pactCode` if a constant or `Support` check reveals it.

## 7. Other protocols to look for

- **WiFi/LAN**: MQTT (`mqtt`, `Mqtt`), LAN discovery/UDP (search `Lan`, `Socket`,
  `Http`), local TCP. Report topics, ports, endpoints and message formats.
- **Matter**: pairing clusters/attributes and how commands map.
- **BLE broadcast / TH broadcast**: advertisement-based sensors (`BleBroadCastInfo`,
  `ThBroadcastUtil`, `Th*`) — report advertising payload/byte layout and parsed readings.
- **IR/RF**: appliance control code sets.
- **ptUrl / multiSync / OTA** as above.

## 8. Readings / notifications

Collate both directions. For each family capture:

- BLE notify/read opcodes and parsing (`*NotifyParse`, `parseValidBytes`, `parse`)
- IoT `status` / `devStatus` / `state` schemas and field names/units
- Sensor readings (temperature, humidity, battery, leak, motion, air quality, etc.),
  including scaling, offsets, min/max and units.
